# Plan Command

`specrun plan -n <name>` starts an interactive Claude Code planning session for a new or existing
spec. The session follows a fixed sequence: context, refine with a checklist, a gate, write-spec,
validation. specrun records the session's token usage in the spec's run log, so planning costs
show up in `history.json` and `specrun stats` next to the task costs. Runs, reviews and the
existing skills behave as before.

| -------------------------------- | ---------------------------------------------------------- |
| README.md (this file)            | Request, analysis, decision log, task overview, questions  |
| [tasks.yaml](tasks.yaml)         | Tasks with phase, needs, model and size — read by specrun  |
| [tasks/](tasks/)                 | One self-contained brief per task                          |
| [TASK_PROMPT.md](TASK_PROMPT.md) | Spec-specific rules added to every task's prompt           |

Run: `specrun run 001-plan-command` (branch `specrun/001-plan-command`, tasks with model `strong`
in [tasks.yaml](tasks.yaml)).

## 2. Analysis

### Interactive Claude Code sessions

- `specrun review` already hands the terminal to Claude Code: `src/cli/commands/review.ts`
  (`runReview`) writes the context to `.specrun/review/<name>.md`, starts
  `claude --append-system-prompt-file <file> <message>` through `runInteractive`
  (`src/process/run.ts`) and refuses without a terminal (`deps.interactive`). `--print` prints
  the prompt instead. `plan` follows the same pattern and the same test seams
  (`ReviewOverrides.launch`).
- `claude` accepts `--session-id <uuid>` (use this id), `-n, --name <name>` (display name) and
  `--resume <id>`. Because specrun picks the session id before launching, it knows which
  transcript to read afterwards.

### Claude Code transcripts

- Interactive sessions are stored as plain JSONL (not gzip) at
  `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<slug>/<sessionId>.jsonl`. The slug is the cwd with
  non-alphanumerics replaced by `-`. specrun doesn't reproduce that rule; it globs
  `projects/*/<sessionId>.jsonl`.
- Every line is one JSON object with `type`. `assistant` lines carry `message.id`, `message.model`
  and `message.usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`,
  `cache_creation_input_tokens`). One API message can span several lines with the same
  `message.id` (one per content block), so lines must be deduplicated by `message.id`. Lines carry
  `isSidechain` (subagent traffic). Newer versions may keep subagent transcripts as `*.jsonl` in
  `projects/<slug>/<sessionId>/subagents/`.
- **No cost field.** Only tokens are recorded (PLD-6). The SDK transcripts the runner writes
  (`src/session/transcript.ts`, gzip, `SDKMessage`) are a different format; `readTranscript` and
  `analyzeSession` are not reused.

### Run log, history, stats

- Events: `src/events/eventSchema.ts` (discriminated union `EventSchema`; unknown types are
  counted, not rejected, so older specrun versions tolerate the new event).
  `src/events/taskState.ts` `deriveState` switches on `t` with a `default` branch.
- CLI code that appends an event outside a run: `src/review/markReviewed.ts` (`createEventStore`
  with `runId: review-<uuid>`). The live events file of a spec is
  `activeSpecFiles(...).eventsFile` (`src/cli/cliDeps.ts`).
- `listSpecs` (`src/spec/loadSpec.ts`) only lists folders with a `tasks.yaml`, so a folder created
  by `plan` before the spec is written is invisible to `run` / `status` / `stats`.
- Archive: `readArchiveSource` / `writeArchive` (`src/archive/archiveSpec.ts`) build `History`
  (`src/archive/history.ts`, `HistorySchema` version 1) from the spec's events. A history is only
  written when there are samples or deviations (`keepHistory`).
- Stats: `src/cli/commands/stats.ts`, `src/stats/aggregate.ts`, JSON shape
  `src/stats/jsonOutput.ts` (`StatsJsonSchema`, read by the feedback skill, SRD-16).

### Skills

- `plugin/skills/{refine,write-spec,feedback}/SKILL.md`, linked into `.claude/skills/` by
  relative symlinks. `src/plugin/templates.spec.ts` checks that every skill folder has a
  `SKILL.md` with `name` = folder name.
- write-spec §4 computes `NNN` itself; with `plan` the folder already exists and must be reused.

### Side effects to keep in mind

- Plan events land in the spec's `events.jsonl` in the main checkout. They must be committed with
  the spec folder before `specrun run`. Otherwise the worktree (created from HEAD) lacks them and
  the later merge can collide with the uncommitted file. `plan` prints this reminder (PLD-5).
- A resumed session appends to the same transcript, so its metrics cover the whole session. Totals
  must count the latest event per session id, not sum all events (PLD-8).
- A folder created by `plan` whose session ended without a `tasks.yaml` stays as an empty spec
  folder. It is harmless (`listSpecs` skips it) and `plan -n <name>` continues it.

## 3. Decision log

Agreed with the product owner on 2026-11-17 (see [Resolved questions](#5-resolved-questions)).
Prefix `PLD-`.

| ID     | Topic                | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PLD-1  | CLI                  | `specrun plan -n, --name <name> [-f, --file <request.md>] [--resume] [--print]`. `--name` is required and must match `^[a-z0-9]+(?:-[a-z0-9]+)*$`; a name starting with digits followed by `-` (e.g. `005-foo`) is rejected with the hint to pass the name without the number.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| PLD-2  | Spec folder          | Active folder `<specsDir>/<digits>-<name>` exists → continue it (no new number). Archived folder `<specsDir>/archive/<digits>-<name>` exists → `SpecrunError('spec-invalid')`, hint "choose another name". Otherwise `NNN` = highest leading number of any folder name in `<specsDir>` and `<specsDir>/archive` + 1, zero-padded to 3 digits (`001` when none), and the folder is created before launching. A spec with a worktree (`specWorkspace(...).kind !== 'checkout'`) is refused: "edit the spec in its worktree".                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| PLD-3  | Launch               | New session: `claude --session-id <uuid> -n "plan <spec>" --append-system-prompt-file <repo>/.specrun/plan/<spec>.md "/specrun:plan <spec>"`. `--resume`: the session id of the spec's latest `plan.session` event → `claude --resume <id> --append-system-prompt-file <file> "Continue planning <spec>."`; no earlier session → `SpecrunError('spec-invalid')`. No terminal → `SpecrunError('terminal-required')` (hint: `--print`). `--print` writes the context and the first message to stdout and creates no folder, file or event. `claude` failing to start → `SpecrunError('claude-missing')` like review.                                                                                                                                                                                                                                                                                                                                            |
| PLD-4  | Context file         | Only facts the model can't get cheaply, nothing gathered from other specs: the spec name and its folder (repo-relative); `new` or the list of files already in it; `specsDir`; the request from `--file` verbatim inside `<request>` tags, or the line "No request file — ask the user for the request."; and the instruction "Write the spec into exactly this folder; don't compute a new number." No deviations or other specs' content. Rendered by a pure function; written to `.specrun/plan/<spec>.md` (`.specrun/` is git-ignored).                                                                                                                                                                                                                                                                                                                                                                                                                   |
| PLD-5  | After the session    | Whatever the exit code: find the transcript (PLD-7), compute metrics, append one `plan.session` event to `activeSpecFiles(repoRoot, config, spec).eventsFile` with `runId` `plan-<sessionId>`. Transcript not found or unreadable → `metrics: null` and a warning on stderr. Then print one summary line (turns, tokens in / out, cache read, peak context, or "no transcript found"). If `tasks.yaml` exists: "Next: specrun status <spec> — commit the spec folder (incl. events.jsonl) before specrun run". If not: "No tasks.yaml yet — specrun plan -n <name> continues". The command's exit code is claude's.                                                                                                                                                                                                                                                                                                                                           |
| PLD-6  | `plan.session` event | `{ t: 'plan.session', sessionId: string, resumed: boolean, exitCode: int, metrics: PlanMetrics \| null }` with `PlanMetrics = { turns, inputTokens, outputTokens, cacheRead, cacheWrite, peakContext, models: string[], subagents: { files, turns, inputTokens, outputTokens, cacheRead, cacheWrite } }` (all ints ≥ 0). Tokens only, no USD. `deriveState` ignores the event.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| PLD-7  | Reading transcripts  | Main file: first match of `<configDir>/projects/*/<sessionId>.jsonl`, `configDir` = `env.CLAUDE_CONFIG_DIR` or `~/.claude`. Subagent files: every `*.jsonl` in `<that dir>/<sessionId>/subagents/` if it exists. Unparseable lines are skipped. A turn is one distinct `message.id` of an `assistant` line with `message.usage` (the last line of an id wins). Main-file lines with `isSidechain: true` and all subagent-file turns count into `subagents`; the rest into the top-level fields. Turn context = input + cacheRead + cacheWrite; `peakContext` = max over main turns; `models` = distinct `message.model` of main turns, in first-seen order.                                                                                                                                                                                                                                                                                                   |
| PLD-8  | History and stats    | `History` gets `planning: { sessions, turns, inputTokens, outputTokens, cacheRead, cacheWrite, peakContext, subagentTokens } \| null` (defaulted to `null`; `version` stays 1, the field is additive). It is computed from the latest `plan.session` event per `sessionId` with non-null metrics; `peakContext` = max, `subagentTokens` = sum of subagent input + output + cacheRead + cacheWrite, the rest are sums. A spec with planning data keeps its `history.json` even without samples. `specrun stats` prints a "Planning" table (SPEC, SESSIONS, TURNS, IN, OUT, CACHE READ, PEAK CTX) under the existing output when any selected spec has planning data; `--json` gets `planning: [{ spec, ...same fields }]` (additive, version stays 1).                                                                                                                                                                                                         |
| PLD-9  | Plan skill           | `plugin/skills/plan/SKILL.md` (name `plan`), linked as `.claude/skills/plan`. Fixed phases: **1 Context**: read the specrun context, CLAUDE.md is already loaded; read only code and docs the request touches. **2 Refine**: follow the refine skill, and before the questions walk the checklist (scope and roles; data model and migration; permissions and security; edge cases and legacy data; UI states and user-visible texts; tests and verify; docs to update; out of scope), marking each item resolved, defaulted (listed in the summary) or not applicable. **3 Gate**: one `AskUserQuestion` "Write the spec now?" (Write the spec (Recommended) / More questions). **4 Write**: follow the write-spec skill into the given folder. **5 Validate**: `specrun status <spec>` until it loads cleanly. Final message as write-spec §8. Never commit unless the user asks. The skill refers to refine and write-spec instead of copying their rules. |
| PLD-10 | write-spec           | write-spec §4 gets: "When the session context names the spec folder (`specrun plan`), use it as is — don't compute a new number or rename it."                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| PLD-11 | Docs                 | Root `README.md`: a "Planning" section (command, phases, what is logged, the commit reminder) and the command in the commands overview. `plugin/README.md`: a row for `plan`. Feedback skill: `stats --json` `planning` is input (e.g. planning tokens vs. the spec's deviations and task costs).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| PLD-12 | Request file         | `--file` is resolved against the cwd with `resolve` (absolute paths as given); an unreadable file throws `SpecrunError('spec-invalid')` naming the file. Decided in review 2026-11-17 (PL-2 deviation; absolute paths fixed in PL-5).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## 6. Out of scope

- USD estimates for planning sessions (no price table).
- Gathering context from other specs or their deviations.
- Recording sessions started without `specrun plan` (plain `claude` + `/specrun:refine`).
- The feature map and its use in planning — spec `002-feature-map`.
