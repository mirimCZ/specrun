# Feature Map

> Archived on 2026-11-17 by `specrun archive`. The full spec folder (briefs, prompts, run log) is in git at `06feef7`: `git ls-tree -r --name-only 06feef7 -- docs/002-feature-map`.

A repository can keep a **feature map**: a maintained, high-level overview of what the
application does. It has one Mermaid diagram plus one short doc per feature (purpose,
capabilities, expectations, pitfalls, code references). specrun defines the standard, checks it
with `specrun features check` and keeps it current. Planning reads the map, each spec ends with a
task that updates it, and review files feature-specific lessons into it. Repositories without a
feature map behave as before.

| Document                         | Contents                                                   |
| -------------------------------- | ---------------------------------------------------------- |
| README.md (this file)            | Request, analysis, decision log, task overview, questions  |
| [tasks.yaml](tasks.yaml)         | Tasks with phase, needs, model and size — read by specrun  |
| [tasks/](tasks/)                 | One self-contained brief per task                          |
| [TASK_PROMPT.md](TASK_PROMPT.md) | Spec-specific rules added to every task's prompt           |
| PROGRESS.md                      | Task status and run log, generated by specrun — don't edit |

Run: `specrun run 002-feature-map` (branch `specrun/002-feature-map`, tasks with model `strong`
in [tasks.yaml](tasks.yaml)).

## 2. Analysis

### Where things live

- Config: `src/config/configSchema.ts` (`ConfigSchema`, strict, defaults). Specs live under
  `specsDir` (default `docs`). `listSpecs` only lists folders with a `tasks.yaml`, so
  `docs/features/` is never mistaken for a spec.
- tasks.yaml: `src/spec/specSchema.ts` (`TaskSchema` is a `strictObject`; `SpecSchema` transform
  picks the fields it passes on). A new task field must be added there or every spec using it
  fails to load.
- YAML parsing: `yaml` (dependency), used by `readYamlFile` in `src/spec/loadSpec.ts`. Issue
  formatting: `formatIssues` in `src/config/loadConfig.ts`.
- CLI subcommands: one file per command in `src/cli/commands/`, registered in
  `src/cli/program.ts`. Pattern for a check-style command printing problems:
  `src/cli/commands/status.ts`.
- Plan context and skill (from spec 001): `src/plan/planContext.ts` (`renderPlanContext`),
  `plugin/skills/plan/SKILL.md`.
- Review instructions: `src/review/reviewPrompt.md` §2 "Where rule fixes go, by kind".
- write-spec: `plugin/skills/write-spec/SKILL.md` and `templates/` (`tasks.yaml`, `task.md`).
  `src/plugin/templates.spec.ts` parses the filled `tasks.yaml` template with `SpecSchema`.

### Mermaid nodes

A flowchart node is defined by an id directly followed by a shape bracket: `id[Label]`,
`id(Label)`, `id{Label}`, `id([Label])`, `id[[Label]]`, `id>Label]`. It can appear alone on a line
or inside an edge line (`a[A] --> b[B]`). Plain ids in edges (`a --> b`) reference nodes without
defining them. Lines starting with `subgraph`, `end`, `%%`, `classDef`, `class`, `style`,
`click`, `linkStyle` and the `flowchart` / `graph` header define no feature nodes. A full Mermaid
parser is not needed (FMD-3).

### Side effects to keep in mind

- Feature ids in `tasks.yaml` are checked by `features check`, never by `loadSpec`. A stale id
  must not stop `specrun run`.
- The map-update task runs last in every spec. It sees all tasks' notes and deviations because it
  `needs: all`. It may run read-only git (`git log --stat`); the protocol forbids only git commands
  that change state.

## 3. Decision log

Agreed with the product owner on 2026-11-17 (see [Resolved questions](#5-resolved-questions)).
Prefix `FMD-`.

| ID     | Topic                 | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------ | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FMD-1  | Location and ids      | Config `featuresDir` (default `docs/features`, repo-relative). Map: `<featuresDir>/README.md`. Feature doc: `<featuresDir>/<area>/<name>.md`; feature id `<area>/<name>`, both parts kebab-case (`^[a-z0-9]+(?:-[a-z0-9]+)*$`). No `<featuresDir>` → the repo has no feature map and every feature-map step is skipped.                                                                                                                                                                                                                                                                |
| FMD-2  | Map README            | H1, one intro paragraph, exactly one fenced `mermaid` block (a `flowchart`, one `subgraph` per area), then a `## Features` table with columns `ID \| Title \| Summary`; the ID cell is a link `[<id>](<id>.md)`; one row per feature, sorted by id.                                                                                                                                                                                                                                                                                                                                    |
| FMD-3  | Diagram nodes         | Node id of a feature = its id with `/` and `-` replaced by `_` (`board/fog-cells` → `board_fog_cells`). Every feature must have a node **defined** with a label (`<nodeId>` followed by `[`, `(`, `{` or `>`) inside the mermaid block. Every defined node must belong to a feature. Edges are free (`A --> B` = A uses B) and not checked. Lines starting with `subgraph`, `end`, `%%`, `classDef`, `class`, `style`, `click`, `linkStyle`, `flowchart`, `graph` are ignored. Two features mapping to one node id is an error. Regex-based, no Mermaid dependency.                    |
| FMD-4  | Frontmatter           | YAML frontmatter, strict: `id` (= path), `title`, `status: draft \| verified`, `depends_on: id[]` (default `[]`), `code: path[]` (min 1), `tests: path[]` (default `[]`), `specs: string[]` (default `[]`, spec folder names). Paths are repo-relative files or folders, no globs. Only a human sets `verified`; agents keep the status they found (new docs start as `draft`).                                                                                                                                                                                                        |
| FMD-5  | Body and detail level | Sections in this order: `## Purpose` (1–3 sentences: what problem, for whom), `## Capabilities` (3–10 bullets, each "who can do what / what happens", user level), `## Expectations` (invariants that must hold: rules, permissions, data consistency), optional `## Pitfalls` (known traps, surprising side effects), optional `## Out of scope`. Detail rule: a feature is a whole the user can name and use; **stability test**: renaming a button, moving a panel or restyling must not require a change to the doc. More than 10 capabilities → split the feature.                |
| FMD-6  | `features check`      | `specrun features check` prints `path: message` lines and exits 1 on any error. Errors: map README missing or without exactly one mermaid block; invalid frontmatter; id ≠ path; missing required section; index row without doc or doc without row; feature without node or node without feature; node id collision; unknown `depends_on`; missing `code` / `tests` path; unknown feature id in an active spec's `tasks.yaml`. Warnings (exit 0): capabilities outside 3–10; `specs` entry not found under `specsDir` or its archive. No `featuresDir` → "No feature map" and exit 0. |
| FMD-7  | tasks.yaml            | Optional task field `features: string[]` (default `[]`), passed through `SpecSchema`. `loadSpec` doesn't check the ids (FMD-6 does).                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| FMD-8  | Upkeep per spec       | When the repo has a feature map, write-spec fills `features` per task and adds a last task "Update the feature map" (`needs: all`, size S, model default) from the template `templates/feature-map-task.md`. The brief: update the docs of the touched features from the tasks' notes and deviations in the prompt plus `git log --stat`; add the spec to `specs:`; a new feature gets a doc (`draft`), an index row and a node; obey the detail rule (FMD-5); run `specrun features check`. Without a map no such task.                                                               |
| FMD-9  | Planning              | The plan context (`renderPlanContext`) adds the map README path when `<featuresDir>/README.md` exists, else "No feature map". Plan skill phase 1: read the map README, then only the docs of features the request touches. The refine checklist gains "feature map impact (features touched, new features)".                                                                                                                                                                                                                                                                           |
| FMD-10 | Pitfalls via review   | `reviewPrompt.md` §2: a lesson tied to one feature → that feature doc's `## Pitfalls` (when the repo has a map); `test-trap` → test docs; a project-wide `constraint` → CLAUDE.md. Without a map, review behaves as today.                                                                                                                                                                                                                                                                                                                                                             |
| FMD-11 | Standard location     | The standard lives in the skill `plugin/skills/feature-map/SKILL.md` (format, detail rule, how to update a doc; how docs feed documentation and test plans: capabilities → acceptance criteria / scenarios, expectations → negative tests, `tests:` → coverage). Templates `templates/README.md` and `templates/feature.md`. Other skills point to it instead of repeating it. Bootstrapping a map is spec 003.                                                                                                                                                                        |
| FMD-12 | Stray docs            | A `.md` file under `featuresDir` at another depth than `<area>/<name>.md` (other than the map README) is a warning and is not loaded as a feature doc; a misplaced doc listed in the index still errors as "row without doc". Decided in review 2026-11-17 (FM-1).                                                                                                                                                                                                                                                                                                                     |
| FMD-13 | No globs              | `FeatureFrontmatterSchema` rejects `code` / `tests` entries containing `*?[]{}`, so the error names the cause instead of "missing path". Decided in review 2026-11-17 (FM-1).                                                                                                                                                                                                                                                                                                                                                                                                          |
| FMD-14 | Map presence          | Planning treats the repo as having a map when `<featuresDir>/README.md` exists (`featuresDir` always has a default); `specrun features check` still reports a folder without README as an error. Decided in review 2026-11-17 (FM-4).                                                                                                                                                                                                                                                                                                                                                  |
| FMD-15 | Task type             | `SpecTask.features` is optional in the TypeScript type so hand-built test tasks needn't spell it out; the schema always fills it and consumers read `features ?? []`. Decided in review 2026-11-17 (FM-2).                                                                                                                                                                                                                                                                                                                                                                             |

## 6. Out of scope

- Bootstrapping a map for an existing repo — spec `003-feature-map-bootstrap`.
- Checking diagram edges against `depends_on`.
- Generating user documentation or test plans (the standard only describes how docs feed them).
- An audit that compares the map with code changed outside specrun.
